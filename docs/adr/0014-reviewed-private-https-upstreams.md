# Reviewed private HTTPS upstreams

Workspaces sometimes need an HTTPS service that the operator runs on a private network, such as an internal API gateway that holds model-provider credentials. Every DNS-derived destination must still be publicly routed, so an allowed name can never rebind the proxy onto loopback, link-local, Seter, or LAN services. The only exception is an explicit `private-http` Policy Grant. It pins one exact hostname to one literal RFC 1918 or shared-address-space (100.64.0.0/10) IPv4 address, for one workspace, on intercepted HTTPS port 443 only. The proxy connects to that literal without resolving the name. The workspace DNS listener answers the name locally with the same address, so the host's rebinding protection stays enabled for every other name. The proxy account's nftables output boundary admits exactly the union of reviewed addresses on port 443, after its host-local and workspace rejects. SNI and authority matching, credential binding, response redaction, and auditing are unchanged, and the name cannot also be a Host Pattern match, passthrough host, repository host, or direct-TCP destination.

We rejected three alternatives. Accepting private DNS answers for selected names would let whoever controls that DNS move the credential-bearing connection. Literal-address HTTP grants cannot carry the hostname needed for SNI and virtual-host routing. Host-side relays outside the proxy would bypass its policy and secret handling. Observed traffic never proposes this grant, because a denial cannot show which private address is intended.
